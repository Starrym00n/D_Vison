> 现状代码：`code/main.py`（25 行 MaixPy Demo）

## 0. 结论速览

| 项目 | 判定 | 说明 |
|---|---|---|
| 总体技术路线（单目巡线 + 地标计数 + UART 事件） | **可行** | 与赛题“不得借助车身外装置”的限制相容，MaixCAM2 算力足够 |
| 巡线（get_regression + PID） | **可行，但当前实现需重做** | 必须是“带 ROI 的选线跟踪”，不能全图单阈值拟合 |
| ⊥ 特征计数定位 | **思路正确，语义有缺口** | 两段赛程里“第 3 个 ⊥”指向的地标不同，方案未定义计数起点 |
| 仅靠“事件触发 + 控制端开环泊车” | **风险最高（最大缺口）** | 库宽 23cm、车宽 ≥15cm，实际可用横向余量仅 ±2~3.5cm |
| UART 通信 | **可行但过窄** | 建议由“只报事件”升级为“事件 + 相对库位的 Δy/Δθ” |

一句话：**方向对、地标选得对（⊥ 确实是场地上最稳的特征），但“视觉只负责报数、泊车全靠开环”这一层撑不住 23cm 库位的精度要求，需要把视觉输出从“离散事件”提升为“几何量”。**

## 1. 赛题关键约束（从 PDF + 图 1/2/3 复原）

### 1.1 场地几何（长度单位 cm）

```
        ← 西                                                                        东 →
   ┌────────┬────────┬────────┐                          ┌──────┬──────┬──────┐
   │  库6   │  库5   │  库4   │        （无地标直道）      │ 库3  │ 库2  │ 库1  │
   │ 50×25  │ 50×25  │ 50×25  │←──── h ──── 50~70 ────→ j ┤23×35 │23×35 │23×35 │
   └────────┴────────┴────────┘                          └──────┴──────┴──────┘
 m ──────────────────────────────────────────────────────────────────────── w ──── n
                                                                            │ 60
   u ───────────────────────────────────────────────────────────────────── v
                    道路（mn 与 uv 之间）宽 45
```

| 地标 | 含义 | 关键尺寸 |
|---|---|---|
| 线段 **mn** | 所有“库口线”重合的直线（1.8cm 黑胶带），贯穿全场 | 全场最长的一条线 |
| 线段 **uv** | 道路边缘线，与 mn 平行 | mn↔uv = **45cm** |
| h | 库4 的东南角 | h→j（无地标直道）= **50~70cm** |
| j | 库3 的西边线 | — |
| w | 库1 的东南角 | w→n = **60cm**，发车区 1 在此区间 |
| 库1/2/3 | 倒车入库车位（口朝 mn，库内箭头**朝南**） | 宽 **23** × 深 **35** |
| 库4/5/6 | 侧方车位（口朝 mn，库5 箭头**朝西**） | 长 **50** × 深 **25** |

### 1.2 车辆与失误约束

* 必须为**前轮转向式四轮车**（不能差速转向/履带/麦克纳姆 → 巡线 PID 的输出是**转向舵机角**，不是左右轮速差）。
* 车长投影 ≥25cm，车宽投影 ≥15cm，车高（含检测装置）**≤30cm**；检测装置不得超出车身外沿。
* 失误①：车身投影覆盖库2/库5 的库边线；失误②：覆盖 uv；失误③：覆盖库1/3/4/6 任一库区。
* 入库前**停顿 1s** 并发第一声蜂鸣，到位发第二声蜂鸣；T1/T2 >40s 记 0 分；到位停 5s 后出库，出库 ≤20s。
* 场地铺白纸，黑线用 **1.8cm 宽黑胶带**；**蓝色字符与蓝色线段在实际场地不画**（只有黑胶带可利用）。

### 1.3 由此推出的两条“硬指标”

1. **横向精度**：库宽 23cm、胶带宽 1.8cm ⇒ 车位内净宽约 21.2cm；车宽 16cm 时单侧余量仅 **±2.6cm**（车宽压到 15cm 也只有 ±3.1cm）。**整个倒车入库动作的横向误差必须 ≤±2cm。**
2. **两个阶段的镜头方向相反**：巡线阶段车头朝西（相机前视才能看见 mn）；倒车入库阶段车是**倒着**向东进库，前视相机此时看不到库口，只能看到西侧道路。

## 2. 逐条可行性评估

### 2.1 巡线：可行，但“全图 get_regression + PID”不够用

**方案原文**：相机固定高度，用 `maix.image.Image.get_regression` 取 `theta`（轨迹线角度）与 `rho`（线到画面左上角距离），用 PID 巡线。

**评估**

* ✅ 机制正确。车沿 mn 西行、右侧距 mn 5cm，mn 在画面中是**一条向消失点收敛的斜线**（并非俯视图里的“水平线”，方案原文用图面视角描述不严谨），而 `theta/rho` 正是为这种“车道线透视成像”设计的量；`main.py` 中 `theta = 90 - theta / 270 - theta` 的归一化也是 Sipeed 巡线例程的标准写法。
* ❌ **画面里同时存在多条黑线**：mn、uv（45cm 外，同侧）、库边线（35cm 长竖直胶带）、库内黑色箭头、邻库深色车模。`get_regression` 是对二值图连通域作直线拟合，而胶带在整个场地上是**连通**的（mn 与所有库边线相交成 ⊥），全局拟合会被竖直库边线拉偏，`rho` 跳变 → PID 发散。**必须加 ROI + 候选线筛选 + 帧间关联。**
* ❌ **横向位置**：车中心到 mn 约 12.5cm（车宽 16cm）。按 HFOV 70°、车头前视估算：前方 30cm 处偏轴角 atan(12.5/30)≈23°，落在画面右缘约 82% 处；20cm 处已出画。即**有效区域只有画面右侧约 1/3**，左侧 2/3 是空路面。
  → 建议：相机**右偏安装 15°~25°**（或加偏心支架让镜头正对车道线），ROI 取右半幅下部；不要指望画面中心。
* ❌ **分辨率**：`main.py` 用 320×240，1.8cm 胶带在 50cm 外仅占 2~4 像素，`theta/rho` 量化噪声大。**建议 640×480**（MaixCAM2 跑得动），并开 ROI 降耗时。
* ⚠️ **安装几何**：相机必须在车身投影内且总高 ≤30cm。建议高度 10~15cm、光轴下俯 **30°~40°**：太陡只看得到车头前 20cm，太平则胶带被压缩成 1~2 像素。
* ⚠️ 胶带是**反光面**（`pictures/4.jpg`、`5.jpg` 实拍可见镜面高光），阈值要用 L 通道上界 + 形态学开运算压高光与噪点，不要只用一个 `[[0,80,...]]` 硬阈值。

**结论**：巡线环节可行，但真正要写的是“**ROI + 选线 + 滤波 + 标定**”，`get_regression` 只是其中最不重要的一行。

### 2.2 ⊥ 特征识别与计数：特征选得对，计数语义必须重新定义

**方案原文**：检测“⊥”型特征并计数，检测到第 3 个后给控制端发信号，控制端把车开到停车位置完成出入库，“并对计数清 0”。

**评估**

* ✅ ⊥ 是场地上**唯一稳定、可重复、可区分**的地标（mn 与库边线相交的 1.8cm 胶带交叉点）。`pictures/4.jpg`、`5.jpg` 实拍证实该特征在真实纸面+胶带下清晰可见——方案选它是对的。
* ❌ **“第 3 个 ⊥”在两段赛程里不是同一个点**（这是最需要在方案里补上的语义）：
  * **倒车入库段**（发车区1 西行）：车静止时库1 东边线（w 处）的 ⊥ 就在车头前 5~30cm，很可能开机第一帧就在画面内。把它计入则顺序为 ① 库1东边线 ② 库1|库2 ③ **库2|库3** ④ 库3西边线(j)；“第 3 个”= 库2 西边线，用于触发倒车尚属合理（但偏西，需与控制端轨迹一并标定）。**若因“起步后才开始计数”漏掉 ①，则“第 3 个”变成 ④(j)，车会多跑 23cm，直接压库3 或撞邻库车。**方案未定义“计数从何时开始、何时有效”。
  * **侧方入库段**（从库2 出库后西行）：若清 0 后重新计数，车从库2 附近出发，依次遇到 ② 库2|库3（可能已过）③ 库3西边线(j) ④ h（库4东边线）⑤ 库4|库5 ⑥ 库5|库6。此时“第 3 个”= **h**（库4 东边线），距目标库5 还有 100~150cm，**明显太早**；侧方泊车真正需要的触发点是“库4|库5 这条线到达车尾位置”（⑤）。
  → 建议：**不要用无锚点的绝对计数**。把“50~70cm 无任何地标的直道 hj”当作天然分隔锚点：巡线中检测到“连续 ≥40cm 无 ⊥”即切到侧方段并复位计数，之后**第 2 个 ⊥（库4|库5）**作为侧方倒车触发点；倒车入库段用“起步后第一个 ⊥（w）”作计数基准。每个触发点都必须是“**锚点 + 序号**”，而不是裸序号。
* ⚠️ **误检源**：库1/2/3 库内的黑色箭头（图 1/2 中箭头为黑色，且“车头方向与箭头相同”说明它实际画在场地内）、库1/库3/库4/库6 的**深色邻库车模**、库边线顶端与 uv 端点。计数必须做**多帧确认（连续 N 帧）+ 里程门控（两次事件间最小行驶 ≥15cm）+ 位置门控（限定在 mn 交点附近、画面右半幅）**，否则单帧阈值 blob 无法区分箭头与 ⊥。
* ⚠️ 需向赛区确认：相邻库之间是**一条共用胶带**还是**两条并排胶带**。若是两条，每个分隔处会产生 2 个 ⊥，计数规则要翻倍。

### 2.3 “只传事件、控制端开环泊车”：这是方案最大的可行性缺口

**评估**

* ❌ 触发事件只能告诉控制端“**现在**该动了”，无法告诉它“**车现在偏了多少**”。而最后 90° 倒车入库的横向误差几乎 1:1 传递为入库后的横向误差（开环轨迹相对车体是固定的）。触发时刻的重复性受车速、曝光、阈值、胶带反光共同影响，出现 3~5cm 误差很容易——而余量只有 ±2.6cm。
* ⚠️ 出库阶段同样有问题：T1/T2 只考核入库，但**失误①②③ 全程判定**，出库时车头摆出压 uv 或扫入库3/库1 一样扣分。方案完全没有描述出库阶段的视觉。
* ✅ 时间上非常宽裕：T1/T2 上限 40s，事件延迟（几十 ms）+ 泊车动作（几秒）都不构成风险。**精度才是唯一瓶颈，不是速度。**

**改进建议（按性价比排序）**

1. **触发帧同时上报几何量**：报“第 N 个 ⊥”的同时，把库2（或库5）两条库边线在图像中的位置 + mn 的 `rho/theta` 一并解算，输出**车体相对目标库中线的横向偏差 Δy(mm) 与航向偏差 Δθ(0.1°)**。单目 + 已知地面平面（相机外参固定）即可用查表/单应反投影得到，不需要新增硬件。
2. **倒车过程中持续回传**（可选但收益大）：倒车时车头朝西、库在东侧后方，前视相机看不到库口，但**能看到库1|库2 库边线从画面右缘向后掠过**，可用其像素运动估计相对位移做“半闭环”。若要真正闭环，可选：
   * 双相机（MaixCAM2 仅 1 路 MIPI，第二路需 USB 或另配模块）；
   * 单相机 + 舵机云台，倒车阶段把镜头摆到“倒车影像”位（注意装置不得超出车身外沿，云台必须完全在车体投影内）；
   * 或**把相机装在车尾/车底朝后下方**：巡线时用“后视巡线”（车沿 mn 西行，后视相机同样能看到 mn 及其与库边线的 ⊥），倒车时正好直视库口——**一颗相机兼顾两个阶段**，值得认真评估。
3. **邻库有车时额外利用车模**：要求 6 明确“邻库有车时应与邻库车头车尾对齐停车”。在测试（1）（2）（5）中，库1/库3/库4/库6 里的深色车模本身就是极强参考（“两块深色夹一个白色空库”），可用于**双重校验计数结果**并控制前后对齐深度。测试（3）（4）（6）无车时必须退化到纯计数。建议做成“有车/无车自适应”。

### 2.4 工具链与其他

* MaixCAM2（AX630C，3.2 TOPS NPU）+ MaixPy + UART：够用。**不必上神经网络**，经典 CV 更快更可控；NPU 留作“多类别地标”的后备方案。
* OpenCV：MaixPy 内置 image 模块已覆盖二值化/形态学/拟合，无需额外引入（引入反而增加部署复杂度）。
* UART 占用 TXD/RXD + 可选 1 个 GPIO：可行。建议该 GPIO 用作**控制端→视觉端的硬同步线**（如“看到上升沿就复位计数”），比纯软件命令可靠，也能在串口异常时兜底。

## 3. 代码框架与逻辑梳理

### 3.1 现状（`code/main.py`，25 行）

```
camera(320x240) → 每帧 get_regression(单阈值) → 遍历所有线画线 → 归一化 theta → 屏幕显示
```

问题清单：

| 位置 | 问题 |
|---|---|
| `thresholds` | 仍是 Demo 的**绿色**阈值，与场地（白纸+黑胶带）无关 |
| 分辨率 | 320×240 偏小，1.8cm 胶带远景仅 2~4px |
| ROI | 无。全图拟合，必被库边线/箭头/车模污染 |
| 选线 | `for a in lines` 只画不选，没有“用哪条线”的策略 |
| `theta` 归一化 | 直接覆盖原值，且没有“线丢失”的分支 |
| 控制 | 无 PID、无串口、无状态机、无事件上报 |
| 结构 | 单文件脚本，无配置/标定/回放入口，现场调参只能改代码 |

**即：目前还没有“框架”，只有一段 Demo。**

### 3.2 建议的视觉端框架（MaixCAM2 侧）

```
code/
├─ main.py                 # 入口：初始化 → 主循环 → 感知状态机 → 上报
├─ conf.py                 # 现场可调参数：LAB 阈值、ROI、相机安装外参、目标 rho、事件门限
├─ vision/
│  ├─ preprocess.py        # 分辨率/ROI/LAB 二值化/形态学/高光抑制
│  ├─ line_follow.py       # 巡线：候选线筛选 + 帧间关联 + 输出 (lateral_mm, angle_deg, conf)
│  ├─ landmark.py          # ⊥ 检测与计数：扫描线法 + 多帧确认 + 里程门控 + 锚点分段
│  ├─ geometry.py          # 像素↔地面：单应/查表；相对目标库位的 Δy、Δθ 解算
│  └─ overlay.py           # 调试叠加：ROI 框、拟合线、计数、Δy/Δθ（比赛时可关）
├─ comm/
│  └─ uart_link.py         # 帧封装/校验/收发队列/心跳/超时
└─ tools/
   ├─ record.py            # 录制原始帧序列（现场取证 + 离线调参）
   ├─ replay.py            # 离线回放：不接硬件跑算法，输出 CSV(帧号, rho, theta, 事件)
   └─ calibrate.py         # 标定：地面棋盘/钢尺 → 单应矩阵与外参表
```

**核心数据流**

```
camera.read()
   └→ preprocess(img) ──→ lines = get_regression(thresholds, roi=ROI_ROAD, area_threshold=…)
          ├→ line_follow.select(lines, prev)  → (lateral_mm, angle_deg, conf)
          ├→ landmark.detect(bin, roi)        → List[Mark(idx, x_px, y_px)]
          └→ geometry.solve(bin)              → (Δy_mm, Δθ_deg)   # 触发帧/需要时
   └→ tracker.step(...)      # 感知状态机：SEARCH → FOLLOW → WATCH → REPORT → WAIT_ACK
   └→ uart_link.send(...)    # 巡线态 25~50Hz；事件重复 3 帧 + ACK；心跳 10Hz
```

### 3.3 控制端（MCU）侧框架

```
firmware/
├─ main.c                  # 初始化 + 主循环（1kHz 控制 / 100Hz 规划 / 事件驱动状态机）
├─ bsp/   motor.c servo.c encoder.c imu.c uart.c buzzer.c
├─ ctrl/  line_pid.c      # 巡线：输入 Δy/Δθ → 前轮转向角；速度环（编码器）
│         steer.c         # 前轮转向标定：舵机 PWM ↔ 前轮转角
├─ plan/  park_reverse.c  # 倒车入库：圆弧+直线段（离线按车体几何生成，落成距离/角度序列）
│         park_parallel.c # 侧方入库：两段圆弧
│         odom.c          # 里程计 + IMU 航向（航迹推算）
└─ fsm.c                  # 比赛流程状态机
```

**流程状态机（控制端）**

```
IDLE
 └─(一键启动)→ RUN_LINE_1        巡线西行，消费 vision 的 lateral/angle，PID 转向
        └─(事件 MARK#k / Δy 进入门限)→ SLOW_DOWN     减速到爬行速度
             └─→ PAUSE_1S + BUZZ1                  # 赛题强制：最后入库动作前停 1s、第一声蜂鸣
                  └─→ REVERSE_PARK_LIB2             # 圆弧段 + 直线段，用 vision 的 Δy/Δθ 修正
                       └─→ IN_POSITION + BUZZ2      # 第二声蜂鸣（T1 计时结束）
                            └─→ HOLD_5S
                                 └─→ EXIT_TURN_RIGHT   # 沿车头方向（朝南）右转出库，≤20s
                                      └─→ RUN_LINE_2   巡线西行（穿过 hj 无地标直道）
                                           └─(锚点+MARK#k / Δy 门限)→ REVERSE_PARK_LIB5
                                                └─→ HOLD → EXIT → DONE
```

**视觉与控制端的职责边界**

* 视觉端**不做决策**（不判断“该不该倒车”），只输出“我在哪、我看到什么、现在有多偏”；
* 触发类事件必须**可重复、可标定**（锚点 + 序号 + 门控），而不是“第 3 个”这种裸计数；
* 泊车轨迹放在控制端（有编码器和 IMU，闭环周期 1kHz），视觉端只在**触发帧与倒车过程中**提供修正量。

### 3.4 UART 协议（建议）

```
帧：0xAA 0x55 | LEN | MSG | PAYLOAD... | CRC8
```

| MSG | 方向 | 载荷 | 频率 |
|---|---|---|---|
| 0x01 LINE_STATE | Cam→MCU | int16 lateral_mm, int16 angle_0.1deg, uint8 conf, uint8 lost | 25~50Hz |
| 0x02 MARK | Cam→MCU | uint8 seg_id, uint8 idx, int16 x_px, int16 y_px, uint16 t_ms | 事件（重复 3 帧，需 ACK） |
| 0x03 GARAGE_GEOM | Cam→MCU | uint8 slot_id, int16 dy_mm, int16 dtheta_0.1deg, uint8 valid | 触发帧 + 倒车中 10~20Hz |
| 0x04 HEARTBEAT | 双向 | uint8 state, uint16 err_cnt | 10Hz |
| 0x80 CMD | MCU→Cam | uint8 cmd(RESET_COUNT/SET_MODE/SET_TARGET), uint8 arg | 按需 |

设计要点：**所有多字节量都用物理单位（mm / 0.1°）**，别让控制端再去解释像素；**事件必须带 ACK 与超时重发**；**丢线要主动上报 lost**，让控制端进入降级策略（里程计盲走）。

### 3.5 关键算法逻辑（伪代码）

**① 巡线选线**

```
def track_line(img, prev):
    bin = threshold_lab(img, ROI_ROAD)      # ROI：右半幅 + 下部；形态学去高光/噪点
    cands = bin.get_regression(area_threshold=…)
    cands = [c for c in cands if 20 < c.theta() < 160 and c.length() > MIN_LEN]
    if not cands: return LOST
    if prev is None: best = max(cands, key=length)             # 首帧：取最长
    else:            best = argmin(cands, |rho(c) - prev.rho|)  # 之后：帧间最近邻
    lateral_mm, angle_deg = geometry.pixel_to_ground(best)     # 单应/查表
    return lowpass(lateral_mm), angle_deg, conf
```

**② ⊥ 检测与计数（扫描线 + 门控）**

```
def detect_marks(bin, roi):
    marks = []
    for row in SCAN_ROWS:                      # 取 2~3 条水平扫描线
        for r in 黑色像素连续段(bin, row):
            if 1.5cm < r.width < 2.5cm 对应像素 and r 上方纵向连续黑段高度 > H_MIN:
                marks.append(Mark(x=r.center, y=row))
    return 融合去重(marks)                      # 同一 ⊥ 在多条扫描线上命中 → 合并

计数门控：连续 N 帧命中同一位置 → 确认 1 次事件
         两次事件之间行驶距离 ≥ 15cm（编码器或图像位移估计）
         分段：检测到“≥40cm 无事件”的长直道(hj) → 复位计数并切段
```

**③ 相对库位几何量（建议新增，精度的关键）**

```
def solve_garage(bin, roi):
    l1, l2 = 目标库两条库边线的像素质心          # 库2 或 库5 的两条竖线
    p1, p2 = inverse_perspective(l1), inverse_perspective(l2)   # → 地面坐标(mm)
    center = (p1 + p2) / 2
    dy     = center.x - car_axis_x                  # 横向偏差
    dtheta = atan2(p2.y - p1.y, p2.x - p1.x)        # 相对库中线的航向偏差
    return dy, dtheta
```

## 5. 需要向赛区/队友确认的问题清单

1. 相邻库之间是**共用一条**胶带还是**两条并排**？（决定 ⊥ 的计数密度）
2. 库内箭头是否真的用黑胶带画在场地内？（决定是否必须区分箭头与 ⊥）
3. 赛区 1.8cm 胶带的品牌/反光程度与现场照明（是否有顶灯直射高光）。

5. 库尺寸 23/35、50/25 是**线中心距**还是**线内净距**？（净距比中心距少 1.8cm，直接影响余量计算）
6. 邻库车模的颜色/材质（是否与胶带同为深色，影响图像分割）。
